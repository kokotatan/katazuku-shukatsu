面接・面談の録音を、文字起こし→構造化ノート→今後への示唆、まで一気に処理してください。

録音は30秒ずつのチャンクに分割済みです。このプロンプトの末尾に次が与えられます:
- `CHUNK_DIR=<絶対パス>` … チャンクの置き場。中に `c-000.wav` から始まる連番の30秒wavが入っている
- `CHUNK_COUNT=<個数>` … チャンクの総数
- `SOURCE_FILE=<絶対パス>` … 元の録画/録音ファイル(日付の推定に使う)

手順:

1. **文字起こし**: `CHUNK_DIR` 内の **`c-000.wav` から最後まで、連番順に全チャンク**を `mcp__voicebox__voicebox_transcribe` に渡し、返ってきたテキストを順に連結して全文を作る。各呼び出しの引数は `audio_path=<チャンクの絶対パス>`、`language="ja"`、`model="turbo"`(Voiceboxで既定の'base'は未DLのことがあるため、DL済みの'turbo'を明示指定する。'turbo'も未DLなら、その旨=「VoiceboxのSettings→キャプチャでモデルをダウンロードしてください」と出力して終了)。
   - **`CHUNK_COUNT` 個すべてを処理すること。飛ばさない。** 空文字/無音が返ったチャンクは `[無音]` として次へ進む。
   - **チャンクを結合して1回で渡そうとしないこと。** Voiceboxは1リクエストにつきWhisperの最初の30秒窓しかデコードせず、しかも全体の長さを`duration`として返すため、**エラーを出さずに冒頭30秒だけの文字起こしが得られてしまう**(2026-07-15に実測確認)。分割してあるのはこのため。
   - 連結時、各チャンクの先頭に録音内の経過時刻を `[mm:ss]` 形式で付ける(時刻 = チャンク番号 × 30秒)。後で該当箇所を録画で聞き直すために必要。
   - Whisperの生の出力を使う。要約・整形・誤字修正はここではしない(固有名詞の誤変換は後段の判断材料になるため、そのまま残す)。
2. **メタ情報の推定**: 文字起こしから、企業名・面談者名(分かれば)・日付を推定する。日付は `SOURCE_FILE` のファイル名に含まれていればそれを優先。曜日を書くときは必ずJSTで検算する。
3. **話者ラベル付け**: 連結した全文を発言単位に区切り、各発言の行頭に話者ラベルを付ける。録音はマイクとシステム音声の混合モノラルで音響的な分離はできないため、これは**内容からの推定**である。
   - ラベルは4種のみ: `奥山:` / `面接官(<姓>):`(名乗りや文脈で特定できたとき)/ `面接官:`(氏名不明)/ `話者不明:`。
   - 判定材料: 質問と回答の構造(質問する側=面接官)、発言内容(本人の研究・経歴・志望動機=奥山。submit.local.md の内容と照合してよい)、名乗り(「人事の◯◯です」等)。
   - **確信が持てない発言(相づち・短文・どちらとも取れるもの)は推測で割り振らず `話者不明:` にする。** 誤った帰属は「本人が言っていないことを言ったことにする」ため、不明のまま残す方が正しい。
   - 面接官が複数で名乗りが無い場合、個人の区別はしない(全員 `面接官:` でよい)。
   - ラベルを付けるだけで、Whisperの生テキストは一字も変えない(固有名詞の誤変換もそのまま)。チャンク境界の `[mm:ss]` も従来どおり残す。
4. **文字起こし全文の保存**: `logs/interviews/<企業>-<YYYY-MM-DD>.txt` に話者ラベル付きの全文を Write で保存(gitignore済み想定。無ければ logs/interviews/ を作成)。
   - **既存ファイルを絶対に上書きしないこと。** 保存名が「企業名+日付」だけで決まるため、同じ企業の面接を同じ日に2回処理した場合や、切り出した短いサンプルを投入した場合に、**別の録音の全文を消してしまう**。書く前に必ず Read/Glob で存在を確認し、既にあれば `<企業>-<YYYY-MM-DD>-2.txt`、`-3.txt` … と連番を振って**新規ファイル**に書く。
   - 特に、**手元のチャンクが元録音の一部分でしかないと疑われる場合**(CHUNK_COUNT が数個しかない/既存全文の一部と内容が一致する等)は、上書きどころか新規保存も保留し、**その旨を報告して指示を仰ぐ**。短い文字起こしで長い全文を置き換えるのはデータ消失にあたる(2026-07-16に60秒サンプルが43分の全文を消しかけた実例あり)。
5. **構造化ノートの作成**: `chrome-prompts/interview-notes.local.md` の既存形式に厳密に合わせた1社分の節を組み立てる。見出しは `## <企業名>(<面談者/種別>)<YYYY-MM-DD>`。中に以下を含める(該当があるものだけ):
   - 位置づけ/手応え(カジュアル面談/選考/最終 等、感触)
   - 面談者の経歴(語られていれば)
   - 得た事業情報・相手の考え(志望動機に効く一次情報)
   - 聞かれたこと・話したこと(想定質問の蓄積に使う。手順3の話者ラベルを根拠にし、`話者不明:` の発言を本人の回答として扱わない)
   - ネクストアクション
   ※捏造しない。聞き取れない/不明な箇所は「(聞き取り不能)」等と明示し、推測で埋めない。
6. **今後への示唆(このパイプラインの肝)**: 上記ノートに続けて `### 今後への示唆` 節を作り、次の観点で具体的に書く:
   1. 志望動機・ESへの反映点(この面談で得た固有情報をどう使うか)
   2. 次選考の対策(次のステップ・準備すべきこと)
   3. フォローアップ(お礼メール/LINE/日程返信など、いつ・誰に・何を)
   4. 懸念・違和感フラグ(相手の反応や自分の発言で引っかかった点)
   5. self-wiki / submit.local.md への更新提案(新しく言語化できた強み・エピソード等。反映は本人判断)
7. **追記**: 作った節を `chrome-prompts/interview-notes.local.md` の「## 自己分析素材」の直前に Edit で挿入する。既存の内容は絶対に壊さない(挿入のみ)。
8. **面接官の顔写真の切り出し(スクショがあるときだけ)**: `SOURCE_FILE` の拡張子を除いたファイル名を `<スラッグ>` として、`logs/interviews/<スラッグ>-shots/` に `shot-*.png`(meeting-autopilot が面談中に撮ったプライマリ画面のスクリーンショット)があるか確認する。無ければこの手順は丸ごと飛ばす。あれば:
   - 各 png を Read で見て、面接官の顔が明瞭に写るフレームを選ぶ(ぼけ・小さすぎ・資料で隠れているものは避ける)。
   - 顔部分の矩形(顔の周囲に2〜3割の余白)を見積もり、ffmpeg で切り出す:
     `ffmpeg -y -i <shotのpng> -vf "crop=w:h:x:y" <同じ-shotsフォルダ>/face-<連番>.png`
     切り出した png は必ず同じ `-shots` フォルダ内に置く(logs/ の外・git管理下・data/ 配下へは置かない)。
   - 切り出した顔が手順9の `people` のどの人物かを対応づけ、該当人物の要素に `photoPath`(切り出した png の絶対パス)を入れる。登録の実体は後段(interview-digest.ps1 → db-apply-interview.ts → photo-sync.ts)が既存の写真パイプライン(data/private/photos への複製 + person_photo.storage_key + bearer認証付き /api/photo-push)で行う。写真の実体は DB・snapshot・git へは入らない。
   - **本人(奥山彪太郎)の顔・自分のカメラ映像(セルフビュー)は絶対に登録しない**(`photoPath` を付けない)。画面共有の資料に写り込んだ顔写真も対象外。
   - どの人物の顔か特定できないとき(複数人で判別不能・名乗りと顔が対応づかない等)は `photoPath` を付けず登録は保留し、手順10のサマリで「顔写真は保留(理由)」と報告する。
   - 既に写真が登録済みの人物には後段が自動で登録をスキップする(上書きしない)ので、明瞭に撮れていれば付けてよい。
9. **DB反映JSONの作成**: 末尾の `DB_JSON` へ、次のキーだけを持つ厳格JSONを Write で新規作成する。Markdownやコメントを混ぜない。
   - `runId`: `APPOINTMENT_ID` が1以上なら `meeting-<予定ID>`。0なら元ファイル名と日付から再実行しても同じになるID
   - `appointmentId`: `APPOINTMENT_ID` が1以上のときだけ数値で入れる
   - `company`, `position`(分かる場合), `occurredAt`(ISO 8601), `title`, `summary`, `transcriptPath`
   - `questions`: `[{question, answer?, feedback?}]`
   - `people`: `[{name, company?, role?, category?, notes: string[], confidence: 0..1, photoPath?}]`。`photoPath` は手順8で切り出した顔写真の絶対パス(該当者だけに付ける。本人には絶対に付けない)
   - **氏名の表記確認(2026-07-28本人指示)**: 新しく登場した人物の氏名は、可能ならWeb検索(「会社名 氏名 採用」等)で
     漢字表記を確認する。文字起こしは同音異字を間違えやすい(実例: 彩子/綾子)。検索で確証が得られないときは
     聞こえたままの表記を使い、`notes` に「氏名の漢字は要確認」と1行残す。名の分からない人は「姓のみ」でよい
     (後からフルネームが判明すれば自動で名寄せ・昇格される)
   - `profileSuggestions`: `[{field, value, confidence: 0..1}]`。fieldは strengths / weaknesses / careerAxis / desiredRole / desiredIndustry のいずれか。確定個人情報は入れない
   - `followUps`: 文字列配列
   発言から確認できない値は作らず、省略または空配列にする。人物メモは追記専用、プロフィールは候補追加であり、確定情報を上書きしない。

10. **サマリ出力**: 企業名・日付・保存先・示唆の要点(特にフォローアップで急ぐもの)・顔写真の扱い(登録候補にした人物/保留とその理由。スクショが無ければ省略)を簡潔に出力し、最終行に単独で `=== interview-digest 完了 ===` と出力する。

注意:
- 全処理はローカル(voicebox)とローカルファイルのみ。外部送信はしない(顔写真のBlob同期は後段の interview-digest.ps1 が行う。このプロンプト内では行わない)。
- 面談内容は機密。文字起こし・ノートは gitignore 済みの場所にのみ書く(logs/ と *.local.md)。
