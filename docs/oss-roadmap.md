# katazuku OSS化の論点整理

最終更新: 2026-07-19

この文書は公開の決定ではなく、将来公開できる部分を安全に切り出し、
初めてダウンロードした人が簡単に使える状態へ持っていくための論点と順序をまとめる。

## プロジェクトの説明

英語では generic job hunting automation とだけ書かない。想定する説明は次のとおり。

> A local-first, human-in-the-loop automation toolkit for Japanese new-graduate recruiting
> workflows, known as shūkatsu. It reduces repetitive coordination while keeping decisions,
> identity verification, assessments, interviews, and final approvals with the applicant.

日本の新卒就活には、卒業年コホート、プレエントリー、マイページ、ES、Web適性検査、
一括採用、面接日程調整など固有の流れがある。28卒は個人設定であり、
OSS本体は卒業年を設定可能にする。

## 公開する部分と非公開にする部分

| 公開候補 | 非公開のままにするもの |
|---|---|
| SQLiteスキーマとマイグレーション | 実データのkatazuku.db |
| 状態機械、遷移規則、冪等化 | 氏名、住所、学校、連絡先、顔写真 |
| CLI、入出力JSON Schema | ES本文、面接記録、メール本文 |
| ブラウザ操作の共通アダプター | Cookie、セッション、認証情報 |
| サイト別アダプターの枠組み | 個人用local promptと企業別提出履歴 |
| カレンダー、メール、ストレージの接続口 | APIキー、合言葉、service account |
| 安全境界と承認ゲート | logs、録音、文字起こし |
| ダミーデータ、テスト、開発用fixture | 本人や面接官を特定できるデータ |
| 汎用プロンプトテンプレート | 実際の回答を含むプロンプト |

DB設計はOSSの価値の中心なので公開候補にする。ただし、公開するのはスキーマ、
マイグレーション、匿名のseed、ER図、データ保持方針であり、個人DBそのものではない。

## 安全性と責任分界

OSS版にもコード側の強制境界を持たせる。

- エントリーとESの最終送信は本人の明示承認を必須にする
- 本人認証、CAPTCHA、SMS、メール認証を回避しない
- 本番Web適性検査やコーディングテストを代理受験しない
- 問題、解答、検査画面を収集しない
- 面接予約は本人が事前指定した空き条件の中だけ自動化する
- すべての外部操作に冪等キーと監査ログを持たせる
- サイトの利用規約、アクセス頻度、robots、API規約を接続先ごとに確認する
- destructiveな操作と辞退は別の強い確認を要求する

プロンプトの注意書きだけでなく、DB API、CLI、ブラウザアダプターの各層で守る。

## 認証と複数ユーザー

現在の個人版は本人1人が前提だが、OSSでは次を分離する。

- ローカル単一ユーザー: 初期設定が最も簡単。localhostとOSの権限で保護
- リモート単一ユーザー: パスキーまたは一般的なOIDCでログイン
- 複数ユーザー: テナント分離、行レベル認可、暗号化、監査、削除・エクスポートが必要

最初のOSS版はローカル単一ユーザーを推奨構成にし、ログイン機能は交換可能なadapterとして設計する。
複数ユーザーSaaSを同時に完成させようとすると、就活自動化より認証と法務の比重が大きくなる。

## 設定とファイル形式

独自XMLは基本的に使わない。

| 用途 | 推奨形式 | 理由 |
|---|---|---|
| 説明、設計、運用 | Markdown | GitHubで読みやすく差分も追いやすい |
| 人が編集する設定 | YAML | コメントを書け、短い設定に向く |
| API、イベント、機械間通信 | JSON | ブラウザとNodeで扱いやすい |
| 入力検証 | JSON Schema | 設定UIやプロンプト生成にも再利用できる |
| 正本データ | SQLite + SQL migration | ローカルで導入しやすく移行を管理できる |
| カレンダー交換 | iCalendar形式のICS | カレンダーの標準形式。XMLではない |
| 秘密情報 | 環境変数またはOS keychain | リポジトリへ入れない |

XMLを使うのは外部標準がXMLを要求する場合だけでよい。例はRSS/Atomの入出力、
SAMLメタデータ、古い求人・大学システムとの連携である。その場合もXMLはadapterの境界に閉じ込め、
内部データはJSONまたは型付きオブジェクトへ変換する。新しい独自設定をXMLで作る利点は小さい。

## プロンプトを簡単に作る将来案

プロンプト本文を毎回手書きするのではなく、次の3層に分ける。

1. workflow.yaml: 目的、必要入力、許可する操作、承認点、完了条件
2. workflow.schema.json: 型、必須項目、禁止項目、UI生成用の説明。
   応募イベントについてはschemas/application-start.schema.jsonと
   schemas/application-event.schema.jsonを最初の実例として追加済み
3. renderer: Claude Code、Codex、ブラウザエージェント向けにプロンプトを生成

サイト固有情報はadapterとして別管理し、個人情報やES本文は参照IDだけを渡す。
将来はフォームUIで選択するとYAMLとプロンプトが生成される形にできる。

## インストール体験

最初の公開版で目指す導入手順は次の範囲。

~~~text
git clone
セットアップコマンドを1回実行
設定ウィザードで卒業年、カレンダー、ブラウザ、保存先を選択
ダミーデータで動作確認
本人データをローカルへ取り込む
~~~

必要な工事:

- Windows、macOS、Linuxで同じCLIが動くようPowerShell依存を薄くする
- NodeとSQLiteの対応バージョンを固定する
- migration、doctor、backup、export、deleteコマンドを用意する
- secret scannerと個人情報scannerをCIへ入れる
- ダミー企業・ダミー選考だけのsample DBを作る
- Chrome以外のブラウザやメール・カレンダーをadapter化する
- connectorがなくてもICS、CSV、手動importで試せるようにする
- 失敗時の再開、dry-run、監査ログ閲覧を標準機能にする

## ライセンスとガバナンス

公開前に決める。

- コードのライセンス。候補はApache-2.0またはMIT
- ドキュメントとプロンプト例のライセンス
- CONTRIBUTING、行動規範、SECURITY、脆弱性報告先
- contributorのDCOまたはCLA
- 商標とプロジェクト名の扱い
- サイト別adapterの保守責任と、壊れた場合の無効化手順

応募の外部送信を扱うため、SECURITYと安全ポリシーは最初の公開コミットに含める。

## Claude for Open Sourceなどへの準備

特定プログラムの募集条件は申請時に公式情報を再確認する。そのうえで、一般に説明できる状態として
次を揃える。

- public repositoryと明確なOSSライセンス
- 日本の新卒就活という固有課題と、誰に何の価値があるかの英語説明
- 5分程度で試せるquickstartとデモ
- 個人情報を含まないissue、roadmap、sample data
- 継続的な開発履歴、テスト、リリース
- CONTRIBUTINGとgood first issue
- セキュリティ、安全境界、データフローの説明
- 実ユーザーまたは協力者のフィードバック
- 提供されたモデル利用枠を何に使うかの具体案

現在は個人プロジェクトの実データと汎用コードが同居しているため、公開申請より先に
境界分離と履歴の機密検査が必要である。

## 公開までの段階

### Phase 0: 個人版で機能を完成

- DB中心化と6入力を実走
- 応募runと承認ゲートを実サイトで検証
- カレンダーoutboxを定期実行
- 適性検査の安全境界を回帰テスト

### Phase 1: OSS境界を抽出

- core、adapter、private configを別パッケージに分ける
- ダミーデータとmigrationを作る
- 履歴を含むsecret・個人情報監査を行う
- 個人用の値を設定ファイルへ移す

### Phase 2: 限定レビュー

- 新卒就活経験者とOSS経験者にセットアップしてもらう
- 就活用語、失敗時の再開、安全確認が伝わるか検証する
- 各社サイトの規約とadapter公開範囲を確認する

### Phase 3: 公開

- まずread-onlyの企業・選考・予定管理とimport/exportを公開する
- 次にフォーム入力支援をopt-inで公開する
- 外部送信は承認ゲートと監査が十分に検証されたadapterだけ有効にする

## 公開判定チェックリスト

- 個人情報と秘密が現在のファイルとgit履歴にない
- sample dataだけで全テストが通る
- fresh環境でquickstartが再現する
- DB migrationとバックアップ復元を検証した
- 送信、辞退、削除に承認ゲートがある
- Web適性検査の禁止操作をコードとテストで防いでいる
- カレンダーとメールの二重作成・二重送信を防いでいる
- ライセンス、SECURITY、CONTRIBUTINGがある
- 日本語と英語で新卒就活固有の文脈を説明している
- 障害時に安全に停止し、再開位置が分かる
