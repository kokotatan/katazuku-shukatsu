Development record / August 2026

Ambient Agentの着眼点を、動く事業へ変え切れなかった。

希少人材との接点を日常業務の中で促すReferral Agentを構想し、操作できるデモまで作りました。受賞には届きませんでした。この記録は、何が評価され、なぜ負け、次はどう本番まで運ぶかを残すものです。

結論

評価されたチームは、着眼点だけでなく「どう解くか」「どの技術とデータ構造で作るか」「実際に動くか」を一つの証拠として見せていた。
一部評価 Agentである必然性

普段の業務へ割り込み、行動を促すAmbient Agentの発想。

未達 課題の解像度

誰のどの失敗を、どの指標で変えるかを最後まで固定できなかった。

未達 Production level

外部API、永続DB、権限、評価を含む実運用の一本がなかった。

課題仮説

「連絡を忘れる」より、「いま話す理由がない」

出発点は、タレントプールが名前の一覧になり、ファーストコンタクト後の関係が続かないという仮説でした。調べるほど、固定周期のリマインドだけでは弱いことが見えてきました。

  • 当初固定周期で未接触を検知し、連絡を促す。
  • 解像度が上がった後前回うまくいかなかった理由を覆す、会社・本人・所属企業の変化を見つける。
  • 本来絞るべき範囲過去に本気で欲しかった一人を再活性化し、自然な一通を送るまで。
  • 最終デモ接点維持、再活性化、候補探索、月次報告、強制措置まで広がり、焦点が薄まった。

提案した体験

チャットを増やさず、普段のSlackで行動を完了する

Agentは自動で人間関係を動かしません。許可された情報を観測し、会社と候補者の変化が重なった時だけ根拠付きで提案し、最後は関係を持つ人が判断する設計です。

  1. 01変化を観測社内更新と公開情報
  2. 02重なりを発見Why now × Why you
  3. 03Slackで提案根拠・接点者・同席候補
  4. 04人が承認編集・相談・送信
  5. 05結果を記録接点・面談・次の一手

Agentとデータ

My Gemを人数分作るのではなく、共通基盤に候補者別の文脈を持つ

Company Agent 権限内のSlack、社内Wiki、Calendar、事業・経営更新から CompanySignal を作る。
Candidate Context Agent X、Zenn、GitHub、登壇、会社公式、許可済み接点記録を候補者別namespaceへ保存。本人発言・公開事実・推測を分離する。
Referral Agent CompanySignal × CandidateContext を照合し、Why now、Why you、接点者、同席候補、送信文を提案する。
Execution layer Slack承認後だけX、Calendar、候補者マスタを更新。冪等キーと監査ログを必須にする。

本番で必要な最小データモデル

SourceRecord出典URL、発信者、公開日、取得日、可視性、content hash、削除状態。
Claim主張、根拠ID、事実／本人発言／推測、確認状態、有効期限。
Relationship候補者、社内オーナー、許可済みチャネル、最終接点、次回条件。
ReferralAction提案、承認者、編集差分、送信時刻、結果、見送り理由。

作ったもの

デモは動いた。本番の価値検証は動かなかった

実装した

  • React/Viteの操作ツアーと状態遷移
  • Slack、X、Calendar、候補者マスタの一連体験
  • 相談、同席候補、面談後メモ、固定周期の接点運用
  • 候補探索、Agent Builder、技術説明
  • localStorageを使うLive Workspace

実装しなかった

  • Slack・X・Calendar等の実API接続
  • 永続DBとバックエンドworker
  • OAuth、ACL、監査、保持・削除制御
  • 実LLM処理と出典評価
  • 実ユーザーへの提供と精度測定

固定ケースで成立した画面上の一致は、本番精度ではありません。ここを明示できなかったことも、完成度への疑問を残しました。

フィードバック

良い発想は、良いプロダクトの入口にすぎない

Ambient Agentがアクションを促す発想は良かった。一方で、課題設定とプロダクションレベルへの落とし込みは不足していた。

敗因は画面数の不足ではありません。一つの課題を、実データ、技術選択、DB、実行結果まで貫通させられなかったことです。機能を足すほど「何が本当に動くのか」が見えにくくなりました。

次の実装順

一人に渡して、翌日も使われる一本を先に作る

  1. 課題を一件へ固定

    過去に本気で欲しかった中途候補一人の再活性化だけを対象にする。

  2. 実コネクタのVertical Slice

    Slack通知、候補者DB、Calendar更新の三点だけを実接続する。公開情報は当初手入力でもよい。

  3. 小さく実提供

    3〜5人の関係オーナー、5〜20候補で4〜6週間使い、送信までの時間と行動変化を測る。

  4. 安全性と運用を実装

    認証、権限、出典、監査、冪等性、失敗時処理、削除伝播を入れる。

  5. 価値確認後に探索を拡張

    Zenn RSS、X公式API、GitHub、Talent Scoutは、一本の価値が確認できてから加える。

提案採用率 編集率 行動完了率 送信までの時間 根拠整合率 不適切提案率
次回は、半日で課題と成功指標を固定する。すぐ触れるモックを渡す。反応を得たら画面を増やさず、実データで動く一本へ変える。

katazukuへ

この失敗を、次のプロダクトの設計原則にする

Ambient Agentは「賢いチャット」ではなく、日常の業務状態を観測し、実行可能な小さな次の一手を作り、結果を監査可能なDBへ残す仕組みです。

katazukuでも、見た目のデモより先に、実データをsource of truthへ集め、決定論的なexecutorと承認ゲートを通して一つの業務を完了させる。この順番を守ります。
